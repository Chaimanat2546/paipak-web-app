# Home Desktop guided review

วันที่เริ่ม: 4 พฤศจิกายน 2026 · Task DSD-001 / F-01 · สถานะ: กำลังตรวจทีละส่วน

คำสั่งเจ้าของ: “จัดทำแผนเช็คแล้วพาฉันเช็คไปทีละส่วน”

## ขอบเขตและวิธีทำ

ตรวจ Home Desktop ใน Pencil และภาพสถานะประกอบที่อยู่ใน F-01 เดิม ใช้ Direction A / Mitr / palette / เจ็ดหมวดและกฎ UX ที่ล็อกไว้ ไม่เริ่ม Mobile, Task อื่น หรือ Frontend

ในแต่ละรอบ: แสดงภาพของจุดเดียว → บอกสิ่งที่ตรวจและสิ่งที่ยังขาด → ถามหนึ่งข้อพร้อมสามตัวเลือกและเหตุผลสั้น ๆ → บันทึกคำตอบเฉพาะจุดนั้น หากต้องแก้ ให้ทำภายในข้อสรุปที่ได้รับจากเจ้าของแล้วนำกลับมาตรวจ ก่อนเลื่อนไปจุดถัดไป

การตอบผ่านเฉพาะจุดไม่ถือเป็นอนุมัติ Home ทั้งหน้า, F-01 ทั้งชุด หรือ DSD-001 ทั้ง Task การตรวจภาพ static ไม่แทนการทดสอบ click, keyboard, query, Auth หรือ backend จริง

## จุดที่ต้องมีหลักฐานเพิ่มตามลำดับ

- Category-specific Results ที่ตรงกับหมวดและ mapping ยังต้องตรวจแบบ ไม่ใช้ Results พัทยาเดิมแทนหลักฐานว่าได้ผลหมวดถูกแล้ว
- Search free query/ranking และนโยบาย capacity/pets จริงยังไม่กำหนดจาก fixtures
- เงื่อนไขปิด date editor ใน booking เป็นคนละส่วนกับ Search และไม่ปิด D-02 จาก flow นี้
- Functional keyboard, focus return, URL, Auth และ external links รอตรวจในขั้น prototype/implementation ที่ได้รับอนุญาต

## ผลจุด 1B / ปลายทางหมวดและค่าที่ส่งต่อ

ฐาน UXD-001 journey-map J-01 กำหนด Home → เลือกหมวด/ค้นหา → Results และ information-architecture เสนอให้ดูทั้งหมดไป Results ของกลุ่มที่เกี่ยวข้องเมื่อมี category mapping ที่ยืนยัน ยังไม่กำหนด URL/query หรือรับรองการจัดบ้านจริงในหมวดจาก fixtures

ตัวอย่างที่หารือ: ผู้ใช้กรอกพัทยาไว้ใน Home และมีข้อมูลค้นหาที่ครบ/ใช้ได้ แล้วกดใกล้ทะเลจากเมนูลัด หรือดูทั้งหมดในแถวใกล้ทะเล ทั้งสองทางเสนอให้ไป Results ของหมวดเดียวกัน คำถามเฉพาะจุดคือจะนำค่าค้นหาเดิมไปด้วยเท่าใด

1. เก็บทุกค่าที่เลือกไว้ (แนะนำ): เพิ่มหมวดใกล้ทะเลโดยคงสถานที่ ช่วงวันที่ครบ คนรวมและ pets ที่เลือกไว้ ช่วยไม่ต้องกรอกซ้ำ
2. เก็บเฉพาะสถานที่: คงพัทยา แต่รีเซ็ตวันที่และจำนวน เพื่อเริ่มสำรวจแบบกว้างขึ้นในเมืองเดิม
3. ใช้เฉพาะหมวด: เปิดใกล้ทะเลทุกพื้นที่ โดยไม่พาค่าค้นหาจาก Home ไปด้วย

ตัวเลือกเหล่านี้เป็นข้อเสนอสำหรับจุดที่ยังไม่ได้ข้อสรุป ไม่ใช่พฤติกรรมที่เปิดใช้งานแล้ว กรณีวันที่ไม่ครบยังต้องใช้ error/recovery ที่ล็อกไว้ ไม่ส่งช่วงวันที่ผิดเป็น query และไม่เปลี่ยนกฎ Back จาก Detail หรือ Booking Intent ที่อนุมัติแล้ว

### คำตอบเจ้าของที่ใช้แทนข้อเสนอเดิม

> 3 เพราะออกแบบมาเพื่อเป็นทางลัดในการไปในหมวดที่ต้องการแล้วค่อยไป search อีกที

ใช้ข้อ 3: กดเมนูใกล้ทะเลหรือดูทั้งหมดของแถวใกล้ทะเล → Results หมวดใกล้ทะเลทั่วทุกพื้นที่ โดยเริ่มสถานที่/วันที่/คน/pets เป็น unset ที่ปลายทาง แล้วให้ค้นหาหรือกรองเพิ่มใน Results ได้ ข้อนี้กำหนดเฉพาะทางเข้าแบบ category shortcut; ปุ่มค้นหาหลักของ Home ยังส่งเงื่อนไขที่ผู้ใช้เลือกตาม flow เดิม การไม่ส่งค่า Home ไปกับ shortcut ไม่ใช่คำสั่งล้างข้อมูลในหน้า Home หรือ Booking Intent

เมื่อใช้ shortcut จะไม่นำค่าร่างของ Search บน Home มาตรวจหรือใช้เป็นตัวขวางทางเข้าหมวด รวมถึงวันที่ที่เลือกค้างไม่ครบ เพราะไม่ได้ส่งค่านั้นไปด้วย ส่วนการกดปุ่มค้นหาหลักยังตรวจ missing checkout ตามกฎเดิม

ยังไม่กำหนด actual route/query keys, ranking, taxonomy mapping ของ fixtures หรือ behavior การปลดหมวดใน Results จากคำตอบนี้ และไม่เปลี่ยน application code/UI ในรอบบันทึกข้อสรุป

## ผลจุด 1C / Browser Back กลับหน้า Home

กรณีตัวอย่าง: อยู่แถวใกล้ทะเลใน Home → กดดูทั้งหมด → Results ใกล้ทะเล → ใช้ Back ของเบราว์เซอร์ คำถามเฉพาะจุดคือให้ viewport ของ Home กลับอยู่ตำแหน่งใด

1. ตำแหน่งเดิม (แนะนำ): คืน section และตำแหน่งเลื่อนแถวเดิม เพื่อดูบ้านต่อจากจุดที่ออกไป
2. เมนูเจ็ดหมวดด้านบน: ช่วยเลือกหมวดใหม่ได้ทันที
3. บนสุดของ Home: เริ่มจาก Header/Hero/Search ใหม่

ทั้งสามตัวเลือกหารือเฉพาะตำแหน่งเลื่อน ไม่ใช่การล้าง Home form/search context และไม่เปลี่ยนกฎ Results ↔ Detail ที่ UXD-001 อนุมัติแล้ว ข้อนี้ไม่รวมกดโลโก้เพื่อกลับหน้าแรก ซึ่งตรวจภายหลังในส่วน Header/Footer

เจ้าของเลือก 1: คืน section และตำแหน่งเลื่อนแถวเดิมบน Home เมื่อใช้ Browser Back จาก Results ใน flow ต่อเนื่อง ไม่เพิ่มการกู้คืนหลัง reload/ปิดแท็บหรือเปลี่ยน Booking Intent

3. ดูทางกลับให้ละเอียดขึ้น: ตรวจตัวอย่างตำแหน่งก่อนเปิดและหลังปิด Auth เพิ่ม โดยไม่เริ่มออกแบบ Auth task

เจ้าของตอบ “แบบนี้ได้” รับ behavior 2D ตามคำชี้แจง Login modal โดยไม่เปลี่ยนหน้า การปิดคง Home เดิมและไม่มี Guest favorites ไม่ขยายผลเป็นการรับแบบ Auth หรือ Home ทั้งหน้า

## ร่างก่อนแก้: 3A / รูปเดียว ไม่มีรูป และรูปโหลดไม่ได้

[ภาพสามกรณี](image-exceptions-r1/UDzK9.png) · [รายละเอียดและข้อจำกัด](image-exceptions-r1/README.md)

ใช้การ์ด Home ปัจจุบันเป็นฐาน มีรูปเดียวซ่อนลูกศรกับ dots; ไม่มีรูปคงพื้นที่ 210px พร้อมข้อความ; รูปที่กำลังดูโหลดไม่ได้ยังเลื่อนไปรูปอื่นและเปิด Detail ได้ ไม่มี Retry ตาม supporting state เดิม หัวใจบน fallback เป็น navy เพื่อให้เห็นบนพื้นอ่อน ตัวอย่าง error แสดง controls ใน hover/focus ไม่ได้เปลี่ยน default controls ทั้ง Home

ถามหนึ่งข้อ: ใช้ภาพทั้งสามกรณีตามนี้ไหม?

1. ใช้ตามนี้ (แนะนำ): แนวการ์ดเท่ากันและยังดูข้อมูลบ้านต่อได้
2. ปรับพื้นที่ไม่มีรูป: ไอคอน ข้อความ หรือพื้น fallback ยังไม่ลงตัว
3. ปรับรูปโหลดไม่ได้: ข้อความหรือความชัดของปุ่มไปต่อยังต้องแก้

รอคำตอบเฉพาะ 3A; ไม่ยืนยัน runtime image error หรือกำหนด catalog publication policy จากภาพนี้


### คำสั่งแก้ 3A จากเจ้าของ

> ปรับ 2-3 ไม่แสดงหากไม่มีรูปแต่ค้นหาแล้วจะเจอ

หน้า Home ไม่แสดงการ์ดบ้านที่ไม่มีรูปในแถวรายการ แต่บ้านนั้นยังค้นเจอในหน้าผลค้นหา ไม่ใช่การลบหรือปิดเผยแพร่ข้อมูลบ้าน การ์ด fallback “ยังไม่มีรูปที่พัก” ใน Image-exceptions-r1 ไม่ใช่แบบที่เจ้าของรับสำหรับ Home ภาพเดิมเก็บเป็นหลักฐานร่างที่ขอแก้ การแสดง fallback ใน Results ยังไม่ได้รับอนุมัติจากคำสั่งนี้

ยังต้องแยกกรณีบ้านมีรูปอื่นที่ใช้งานได้แต่บางรูปโหลดไม่สำเร็จ: เสนอข้ามรูปเสียแล้วใช้รูปที่แสดงได้ ก่อนทำภาพแก้ รอคำตอบเฉพาะกรณีนี้ ไม่เหมาว่ารูปเสียหนึ่งรูปเท่ากับบ้านไม่มีรูปทั้งหมด และไม่อ้างว่าระบบค้นหา/กรองทำงานจริงแล้ว

[ภาพเทียบในแถวเดียว](title-price-r1/RRvp4.png) · [รายละเอียดและข้อจำกัด](title-price-r1/README.md)

เสนอคงชื่อบ้านหนึ่งบรรทัด ย่อด้วย … ตาม supporting state เดิม เพื่อให้ทำเล จำนวนคน ห้องนอน และราคาอยู่แนวเดียวกัน ชื่อเต็มอ่านใน Detail และต้องมี accessible name ในขั้น Frontend เมื่อราคาไม่พร้อมเสนอ “ยังไม่มีข้อมูลราคา” แทนตัวเลข ไม่แสดงเริ่มต้น/ต่อคืน ไม่เดาราคาและไม่ใส่ 0 ภาพนี้ใช้ fixtures ไม่ยืนยันแหล่งข้อมูล ราคา หรือการจองจริง

ถามหนึ่งข้อ: ใช้การจัดข้อมูลตามภาพนี้ไหม?

1. ใช้ตามนี้ (แนะนำ): ชื่อยาวไม่ดันข้อมูลและบอกตรง ๆ เมื่อไม่มีราคา
2. ปรับชื่อยาว: อยากเห็นชื่อมากกว่าหนึ่งบรรทัด
3. ปรับกรณีไม่มีราคา: ข้อความหรือการแสดงการ์ดยังต้องแก้

รอคำตอบเฉพาะ 3B ก่อนตรวจ 3C ไม่ปิด OPEN-007 หรือเริ่ม Frontend จากการตรวจนี้


## ผลจุด 3B / แสดงเฉพาะการ์ดข้อมูลครบ

เจ้าของยืนยัน “ชื่อยาวถูก แต่ถ้าอันไหนข้อมูลไม่ครบไม่ต้องแสดงการ์ดแทน” รับชื่อยาวย่อด้วย … แต่ไม่ใช้การ์ด “ยังไม่มีข้อมูลราคา” บน Home ให้ตัดการ์ดที่ข้อมูลไม่ครบออกและเรียงการ์ดที่พร้อมต่อกัน

[ภาพแก้ Complete-data-r2](complete-data-r2/t87K3A.png) · [รายละเอียด](complete-data-r2/README.md)

ตัวอย่างสมมติบ้าน 02/04 ข้อมูลไม่ครบ จึงแสดงบ้าน 01/03/05/06 ต่อกัน บ้าน 03 ชื่อยาวย่อแบบเดิม ไม่แก้ข้อมูลจริงหรือกำหนด required fields ของระบบจาก fixtures

คำถามหนึ่งข้อ: บ้านที่ขาดราคา/ข้อมูลอื่น ยังให้ค้นเจอไหม?

1. ยังค้นเจอ (แนะนำ): ซ่อนเฉพาะ Home ตามแนวทางกรณีไม่มีรูป
2. ซ่อนจากผลค้นหาด้วย: บ้านที่ขาดราคา/ข้อมูลอื่นรอข้อมูลครบก่อนแสดงใน Results
3. แยกตามข้อมูลที่ขาด: กำหนดข้อยกเว้นเป็นรายชนิดข้อมูล

คำถามนี้ไม่เปิดกฎบ้านไม่มีรูปยังค้นเจอที่ยืนยันใน 3A ใหม่ และไม่ถือว่าการรับชื่อยาวอนุมัติ fallback ใน Results หรือ runtime


เจ้าของเลือก 1: บ้านที่ขาดราคา/ข้อมูลอื่นยังค้นเจอใน Results แต่ไม่แสดงการ์ดบน Home รับเฉพาะนโยบายการมองเห็น ไม่ถือเป็นการอนุมัติ fallback ของ Results หรือการทดสอบค้นหาจริง

## ผลจุด 3C.1 / ทั้งหมวดไม่มีการ์ดพร้อมแสดงบน Home

แยกกรณีโหลดสำเร็จแล้วไม่มีการ์ดที่ข้อมูลครบและมีรูปให้ใช้ ออกจาก loading/error: ยังไม่ทราบข้อมูลเพราะโหลดไม่เสร็จหรือเกิดข้อผิดพลาดไม่ใช่หลักฐานว่าหมวดว่าง รอตรวจ loading/error ในจุดต่อไป

คำถามหนึ่งข้อ: ถ้าหมวดหนึ่งไม่มีบ้านที่พร้อมแสดงบน Home จะให้แสดงส่วนของหมวดนั้นอย่างไร?

1. ซ่อนทั้งส่วนของหมวดนั้น (แนะนำ): หมวดถัดไปเรียงขึ้นมา ไม่มีแถวว่าง
2. คงหัวข้อพร้อมข้อความ: บอกว่ายังไม่มีบ้านพร้อมแสดงในส่วนนี้
3. คงหัวข้อและดูทั้งหมด: เปิดทางไป Results โดยไม่มีแถวการ์ดหรือข้อความว่าง

ทุกตัวเลือกยังคงทางลัดเจ็ดหมวดด้านบนและผลค้นหาตามข้อสรุปเดิม การไม่มีการ์ดบน Home ไม่ใช่การไม่มีบ้านใน Results ไม่ยกเลิก taxonomy ที่ล็อกไว้ ไม่มีภาพแก้หรือ behavior ที่อนุมัติของกรณีทั้งหมวดว่างก่อนเจ้าของเลือก


เจ้าของเลือก 1: หลังโหลดสำเร็จแล้วทั้งหมวดไม่มีบ้านพร้อมแสดง ให้ซ่อนทั้ง section และให้ส่วนถัดไปเลื่อนขึ้นมา ทางลัดเจ็ดหมวดยังคงอยู่ ไม่เปลี่ยนผลค้นหาหรือตีความ loading/error เป็นหมวดว่าง

## ผลจุด 3C.2 / กำลังโหลดครั้งแรก

[ภาพ Loading-r1](loading-r1/NOXpV.png) · [รายละเอียด](loading-r1/README.md)

เสนอโครงร่างการ์ดสี่ใบตามขนาดจริงพร้อมสถานะกำลังโหลด ซ่อน controls ที่ยังไม่มีบ้านให้ใช้งาน ไม่แสดงราคา/รูป fixture เป็นข้อมูลขณะโหลด การ์ดจำลองไม่ใช่รายการบ้านข้อมูลไม่ครบที่โหลดสำเร็จแล้ว หากสำเร็จแต่ไม่มีการ์ดให้ใช้กฎซ่อน section ใน 3C.1 กรณี error รอตรวจ 3C.3

ถามหนึ่งข้อ: ระหว่างโหลดครั้งแรก ใช้แบบไหน?

1. Skeleton ตามภาพ (แนะนำ): เห็นว่ากำลังเตรียมรายการและคงพื้นที่แถวไว้ระหว่างรอ
2. ข้อความ “กำลังโหลด…” อย่างเดียว: หน้าระหว่างรอเรียบกว่า แต่ยังไม่เห็นโครงรายการ
3. ซ่อนส่วนนี้จนโหลดเสร็จ: แสดงเฉพาะข้อมูลที่พร้อม แล้วแทรกส่วนนี้เมื่อมีข้อมูล

รอคำตอบ 3C.2 ก่อนตรวจ error ไม่อนุมัติทั้ง Home หรืออ้างว่าทดสอบการโหลดจริง


เจ้าของเลือก 1 รับ Loading-r1 เฉพาะสถานะโหลดครั้งแรก ใช้ skeleton ตามภาพ ไม่ขยายผลเป็น background refresh หรือทดสอบ network จริง

## ผลจุด 3C.3 / โหลดแถวบ้านไม่สำเร็จ

[ภาพ Listing-error-r1](listing-error-r1/z9TUD5.png) · [รายละเอียดและข้อจำกัด](listing-error-r1/README.md)

เสนอข้อความ error กับปุ่มลองอีกครั้งเฉพาะหมวด ไม่ reload หน้า/ล้างค่าค้นหา/รีเซ็ตหมวดอื่น แยกจากหมวดว่างที่โหลดสำเร็จ ในภาพใช้ panel สูง160px แทนพื้นที่การ์ด362px และคงหัวข้อกับดูทั้งหมด ปุ่ม navy/white เป็น recovery control เฉพาะจุด ไม่ปิด OPEN-001

ถามหนึ่งข้อ: ใช้ error แบบไหน?

1. Panel ตามภาพ (แนะนำ): แจ้งเฉพาะส่วนและมีปุ่มลองใหม่ชัดเจน
2. ย่อเป็นบรรทัดเดียว: ข้อความกับปุ่ม ใช้พื้นที่น้อยลง
3. สูงเท่าแถวการ์ด: คงพื้นที่เดิมระหว่าง loading/error แต่มีพื้นที่ว่างมากกว่า

รอคำตอบเฉพาะ 3C.3; ยังไม่มี retry หรือ API จริง ไม่อนุมัติทั้ง Home จากจุดนี้


### คำตอบยืนยัน 3C.3 จากเจ้าของ

หลังข้อความไม่ชัด ได้ถามยืนยันสามตัวเลือกใหม่ โดยข้อ 1 คือ “ซ่อนทั้งหมวดเมื่อโหลดไม่สำเร็จ เหมือนกรณีไม่มีบ้านพร้อมแสดง” เจ้าของเลือก 1 จึงซ่อน section ที่โหลดไม่สำเร็จและปิดช่องว่าง ไม่ใช้กล่อง error หรือปุ่มลองใหม่บน Home จาก Listing-error-r1 ต้องไม่บันทึกคำตอบนี้เป็นการรับข้อ 1 ของคำถามเดิมที่หมายถึง panel

หมวดที่โหลดสำเร็จ ทางลัดเจ็ดหมวด และค่าค้นหาคงเดิม แยก error กับ empty ในข้อมูลภายใน การซ่อนเป็นข้อยกเว้น presentation เฉพาะแถว Home ตามคำสั่งเจ้าของ ไม่เปลี่ยนข้อกำหนด error/recovery ของ Results/Auth หรืออนุมัติ retry อัตโนมัติ/timeout/reload และกรณีทุกหมวดโหลดไม่ได้ยังไม่มี recovery policy ที่รับรองจากรอบนี้ เก็บ panel เป็น HISTORY ไม่แก้ Main Home fixtures ที่ไม่ได้จำลอง network failure

## ร่างก่อนแก้: 3D.1 / โฟกัสปุ่มในการ์ดเมื่อใช้คีย์บอร์ด

[ภาพ Card-focus-r1](card-focus-r1/ITiqO.png) · [รายละเอียดและหลักฐาน contrast](card-focus-r1/README.md)

แสดง default เดิม คู่กับ photo-focus ที่รับไว้แล้ว และเสนอวงหัวใจเฉพาะ keyboard focus: target44px, white halo36px, face28px พร้อม navy outline2px, ไอคอน22px หัวใจยังไม่ถูกบันทึก ไม่ทำให้วงนี้แสดงตลอดใน default ใช้คู่สี navy/white solid contrast13.74:1 แต่ไม่รับรอง contrast บนทุกภาพหรือปิด OPEN-001

ถามหนึ่งข้อ: ใช้วงโฟกัสหัวใจตามภาพไหม?

1. ใช้ตามนี้ (แนะนำ): เห็นปุ่มที่เลือกและ default ยังเหมือนเดิม
2. ลดความเด่น: วงยังดึงสายตาเกินไป โดยต้องยังมองเห็น keyboard focus
3. เพิ่มความชัด: วงยังแยกจากภาพไม่พอ

รอคำตอบเฉพาะ favorite focus; ไม่ขยายเป็นการรับ accessibility หรือ controls ทุกจุดของ Home


## ร่างก่อนแก้: 3D.1 / หัวใจสีชมพูไม่มีกรอบวงกลม

เจ้าของสั่ง “ต้องเป็นหัวใจสีชมพูสิ่แล้วก็ต้องไม่มีกรอบวงกลมด้วย” จึงแก้เฉพาะภาพ favorite-focus ด้านขวาเป็นหัวใจเส้น #FD6E88 ขนาด22px ลบ halo/face/วงกลมออก คง target44px โปร่งใส หัวใจยังไม่ถูกบันทึก และไม่เปลี่ยน default หรือ photo-focus ที่รับไว้แล้ว

## ผลจุด 3D.1 / หัวใจสีชมพูทึบไม่มีกรอบวงกลม

เจ้าของขอ “ขอแบบ fill” จึงใช้ phosphor/heart-fill สี #FD6E88 ขนาด22px ในภาพด้านขวา คง target44px โปร่งใสและไม่มีกรอบวงกลม ใช้ native icon library ที่รองรับ แก้เฉพาะ appearance ไม่เปลี่ยน Guest Favorites/Login modal หรืออนุมัติ saved/focus semantics ทั้งระบบ

เจ้าของตอบ “โอเค ไปต่อ” รับ appearance หัวใจชมพูทึบไม่มีวงกลมตาม Card-focus-r3 เฉพาะภาพที่ตรวจ ไม่ใช่การรับรอง keyboard/contrast บนทุกภาพ หรือ rollout/Main Home ทั้งหน้า

## ร่างก่อนแก้: 3D.2 / โฟกัสทางลัด ดูทั้งหมด และเลื่อนแถว

[ภาพ Navigation-focus-r1](navigation-focus-r1/oYzOn.png) · [หลักฐาน](navigation-focus-r1/README.md)

แถวบน default/แถวล่าง keyboard focus เสนอกรอบ navy2px บน controls เดิม ทางลัดหมวดยังคงเป็นลิงก์นำทางไม่ใช่ filter toggle และดูทั้งหมดไปหมวดนั้นตามข้อสรุปเดิม ลูกศรที่ disabled ถูกข้ามเมื่อ Tab ไม่เพิ่มกรอบตลอดใน default และไม่เปลี่ยนหัวใจที่เพิ่งรับ

ถามหนึ่งข้อ: ใช้กรอบโฟกัสตามภาพนี้ไหม?

1. ใช้ตามนี้ (แนะนำ): เห็นชัดว่ากำลังเลือก control ไหน โดยหน้าตาปกติคงเดิม
2. ลดความเด่น: กรอบดูแข็งหรือเด่นไป แต่ต้องยังเห็น focus
3. เพิ่มความชัด: กรอบยังมองไม่ชัดพอ

รอคำตอบเฉพาะ 3D.2 ไม่อ้างว่าทดสอบ Tab จริงหรือปิด OPEN-001


## ผลจุด 3D.2 / ออกแบบ focus ทั้งสามจุดใหม่

เจ้าของสั่ง “ปรับใหม่หมด” ในบริบทภาพ Navigation-focus-r1 จึงเปลี่ยนทั้งสาม treatment ที่กำลังตรวจเป็น Navigation-focus-r2: หมวดและดูทั้งหมดใช้เส้นเน้นใต้ลิงก์ แทนกรอบล้อม ปุ่มเลื่อน focused เติมนาวีพร้อมลูกศรขาว เอากล่องพื้นของภาพเทียบออก หัวใจสีชมพูทึบที่รับแล้วไม่เปลี่ยน

[ภาพแก้ Navigation-focus-r2](navigation-focus-r2/oYzOn.png) · [หลักฐานและข้อจำกัด](navigation-focus-r2/README.md)

เส้นและสีเติมแสดงเฉพาะ keyboard focus ไม่ใช่เปลี่ยนทางลัดเป็น selected filter ไม่เปลี่ยนโครง Home หรือ rollout จนรับแบบเฉพาะจุด การตั้ง category targetสูง82px ในทั้งสองตัวอย่างรักษาแนวไอคอน/label ระหว่าง default/focused

คำถามหนึ่งข้อ: ชุดใหม่ใช้ตามนี้ไหม?

1. ใช้ชุดนี้ (แนะนำ): ลิงก์มีเส้นเน้นและปุ่มเลื่อนแยกสถานะด้วยสีเติม
2. ปรับเส้นใต้: ความยาว/น้ำหนักของทางลัดและดูทั้งหมดยังต้องแก้
3. ปรับปุ่มเลื่อน: พื้นนาวีหรือรูปแบบปุ่มโฟกัสยังไม่ลงตัว

รอคำตอบเฉพาะ 3D.2 ไม่เริ่ม Task อื่น Frontend หรือรับรอง actual keyboard จากภาพนี้


เจ้าของเลือก 1 รับ Navigation-focus-r2 เฉพาะภาพ focus ทางลัด/ดูทั้งหมด/เลื่อนแถว ไม่ขยายเป็นการรับรอง keyboard จริง, contrast ทุกภาพหรือทั้ง Home OPEN-001 และ functional verification คงค้าง

โลโก้และรูปบ้านจากหน้าอื่นไป Home ตาม IA ที่รับแล้ว คำถามเฉพาะกรณีอยู่ Home และเลื่อนลงมาแล้วกดสองจุดนี้ จะให้ไปตำแหน่งไหน?

1. บนสุด Home (แนะนำ): กลับไปเริ่มดูหน้าแรก โดยเก็บค่าค้นหาไว้
2. แถบค้นหา Home: ไปเลือกเงื่อนไขต่อ โดยเก็บค่าเดิม
3. คงตำแหน่งปัจจุบัน: ถ้าอยู่ Home แล้วไม่เลื่อนหน้า

ทุกตัวเลือกไม่ล้างค่าค้นหา และไม่เปลี่ยน Browser Back จาก Results ที่คืนจุดเดิม ถ้ามาจากหน้าอื่นปลายทางยังเป็น Home ไม่เริ่มออกแบบ route/หน้าอื่นหรือถือว่าลิงก์กดได้จริงจากภาพนี้


เจ้าของเลือก 1: กดโลโก้หรือรูปบ้าน Header ไปบนสุด Home โดยไม่ล้างค่าค้นหา ไม่เปลี่ยนกฎ Browser Back จาก Results ที่คืน section/ตำแหน่งแถวเดิม ยังไม่ใช่ actual route หรือ scroll test

## ผลจุด 4A.2 / เมนูค้นหาที่พักบน Header

ใช้ Header เดิม awwwD / target rc1GG ตามภาพ header-navigation-r1 ไม่เปลี่ยน appearance ปุ่มนี้เป็นทางเข้าค้นหาจากเมนู ต่างจากปุ่มค้นหาหลักที่ส่งค่าฟอร์ม Home และทางลัดหมวดที่ตกลงไว้แล้ว ประเด็นเงื่อนไขเริ่มต้นยังไม่มีคำตอบตรงในหลักฐานที่ตรวจ

ถามหนึ่งข้อ: กดเมนู “ค้นหาที่พัก” ให้เปิด Results แบบไหน?

1. ที่พักทั้งหมด (แนะนำ): เริ่มทั่วทุกพื้นที่โดยไม่พาค่าฟอร์ม Home หรือหมวดเดิมไปด้วย แล้วค้น/กรองเพิ่มใน Results
2. ตามค่าที่เลือกบน Home: ส่งเงื่อนไข Home ที่ใช้ได้ไป Results เหมือนปุ่มค้นหาหลัก
3. ผลค้นหาล่าสุด: คืนเงื่อนไขที่ Apply ล่าสุดใน flow ต่อเนื่อง ถ้ายังไม่มีให้เริ่มที่พักทั้งหมด

ทั้งสามตัวเลือกไม่บังคับ login/วันที่เพื่อ browse ไม่เปลี่ยนปุ่มค้นหาหลักหรือ category shortcuts ไม่ล้างฟอร์ม Home/Booking Intent จากการเปิด Results หากเลือกข้อ2 ต้องเคารพกฎวันที่ไม่ครบเดิม หากเลือกข้อ3 ยังไม่ถือว่าอนุมัติ storage หรือกู้ Booking Intent หลัง reload/expiry ใช้เฉพาะ applied search context ไม่ใช่ draft filters ยังไม่สร้าง route/query keys หรือทดสอบผลค้นหาจริง


เจ้าของเลือก 1: เมนูค้นหาที่พักบน Header เปิด Results ที่พักทั้งหมดทั่วทุกพื้นที่ ด้วยเงื่อนไขเริ่มต้น ไม่พาค่าฟอร์ม Home หรือ category/filter context เดิมไป ไม่ใช่คำสั่งล้างฟอร์ม Home/Booking Intent ไม่เปลี่ยนปุ่มค้นหาหลักหรือ shortcut หมวด ภาพ Results พัทยาเดิมไม่ใช่หลักฐานของ general Results entry นี้ และยังไม่ทดสอบ route/query จริง

## ผลจุด 4A.3 / ปลายทางเมนูบทความ

Header awwwD มี target IutXx / labelบทความที่รับ appearance ไว้แล้ว แต่ไม่พบปลายทางบทความที่ยืนยันใน registry/open-decisions/approved scope/UXD-001 IA/DSD-001 packet/manifest หรือ Header-r11 README ที่ตรวจรอบนี้ ไม่อ้างว่าตรวจทุก archive หรือมีบทความจริงพร้อมเผยแพร่

คำถามหนึ่งข้อ: เมนูบทความควรไปที่ไหน?

1. หน้ารวมบทความใน papaipak (แนะนำ): อยู่ในเว็บเดียวกัน เป็น navigation contract ของหน้าเนื้อหาที่แยก scope ภายหลัง
2. ลิงก์บทความภายนอก: เจ้าของระบุ URL ก่อนใช้งาน ไม่เดา URL หรือสร้างบัญชี/เว็บไซต์ใหม่
3. ซ่อนเมนูจนเนื้อหาพร้อม: ป้องกันลิงก์ที่ยังไม่มีปลายทาง โดยเป็นการเปลี่ยน visibility ที่ต้องรอเจ้าของเลือก

รอคำตอบเฉพาะปลายทาง ไม่เริ่มออกแบบหน้าบทความ/CMS/content task ไม่สร้างเนื้อหา/claim หรือแก้ Header appearance ก่อนเลือก ข้อสรุป scope หน้าเนื้อหาแยกงานยังคงเดิม


เจ้าของเลือก 1: บทความไปหน้ารวมบทความภายใน papaipak กำหนดเฉพาะ navigation contract ไม่เริ่มหน้าบทความ/CMS/content task และยังไม่กำหนด URL หรืออ้างว่ามีเนื้อหาจริงพร้อมแล้ว

## ผลจุด OPEN-001 / สีข้อความบนปุ่ม

[ภาพเทียบคู่สีแบรนด์](cta-brand-contrast-r1/F9LoP.png) · [หลักฐานcontrast](cta-brand-contrast-r1/contrast-evidence.json) · [คำอธิบายและW3Cอ้างอิง](cta-brand-contrast-r1/README.md)

ไม่เปลี่ยนHome-r8ที่รับappearanceแล้ว เก็บชมพู/ขาวเดิมเป็นvisual referenceตามคำตอบ3พฤศจิกายน และเสนอเฉพาะคู่สีที่ใช้paletteเดิม ไม่ทำชมพูเข้มชุดเก่าซ้ำ

ถามหนึ่งข้อ: OPEN-001เลือกแนวทางไหน?

1. พื้นชมพู ข้อความนาวี (แนะนำ): 5.08:1 คงพื้นชมพูเดิมและผ่านเกณฑ์สีข้อความทั่วไป
2. พื้นนาวี ข้อความขาว: 13.74:1 ผ่านเกณฑ์สีข้อความทั่วไปด้วยpaletteเดิม
3. คงชมพู ข้อความขาว: 2.71:1 และคงOPEN-001ไว้ ไม่ถือว่าแก้contrastแล้ว

รอคำตอบเฉพาะCTAcontrast ก่อนตัดสินscope/stateหรือแก้รุ่นHome ไม่ปิดissue/อนุมัติFrontendเองจากการรับภาพรวม


เจ้าของเลือก3คงชมพู/ข้อความขาวตามเดิมและเก็บOPEN-001ต่อ ได้บันทึกowner-choiceและตรวจnativeHomeว่าพื้น#FD6E88/label#FFFFFFยังคงเดิม ไม่ใช่การอนุมัติaccessibility exceptionหรือfinalfoundation ไม่ถามเลือกสี/เฉดซ้ำโดยอัตโนมัติ
