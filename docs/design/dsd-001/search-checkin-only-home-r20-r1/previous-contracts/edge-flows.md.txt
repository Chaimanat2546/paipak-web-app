# UXD-001 — ทางแยก กรณีผิดปกติ และข้อสรุปเฉพาะงาน

วันที่จัดทำ/ปรับปรุง: 2 พฤศจิกายน 2026 · Asia/Bangkok · รุ่น: review-2 · สถานะ: ภูอนุมัติแล้ว

ตรวจรับเมื่อ 2 พฤศจิกายน 2026 จากข้อความ “อนุมัติ UXD-001 review-2” ดู [บันทึกตรวจรับ](../../../tasks/design/UXD-001.md#owner-acceptance) ไม่อนุญาตให้เริ่ม task ถัดไปอัตโนมัติ

ใช้ร่วมกับ [journey-map.md](journey-map.md) และ [information-architecture.md](information-architecture.md) ตาม [UXD-001](../../../tasks/design/UXD-001.md) เอกสารนี้บอกพฤติกรรมระดับผู้ใช้ ไม่กำหนด endpoint, database schema, กลไก hold, TTL หรือสถานะ enum ของผู้ให้บริการชำระเงิน

**ปัจจุบัน** คือสิ่งที่พบใน demo/source; **เป้าหมาย** อ้างข้อกำหนดที่ยืนยันแล้ว; **ข้อเสนอ** เป็นแนวทาง UX ภายในเอกสาร review-2 ที่ภูตรวจรับแล้ว ส่วน `Q-01` ถึง `Q-05` ภูให้ข้อสรุปตามตารางส่วนที่ 3 รายการ `OPEN-*` และรายละเอียดโดเมนที่ส่งต่อยังไม่ถูกปิดด้วยการตรวจรับนี้

## 1. ตารางทางแยก

| รหัส / เหตุการณ์ | การตอบสนองและทางกลับที่ต้องอธิบาย | ข้อมูลที่ต้องรักษา | หลักฐาน / สถานะ |
|---|---|---|---|
| E-01 ดูรายการโดยไม่ระบุวันหรือจำนวนคน | ให้ดู/ค้นหา/เปิดรายละเอียดได้ ไม่บังคับ Auth; หากเริ่มจองค่อยให้กรอกข้อมูลจองให้ครบ | เงื่อนไขที่เลือกแล้ว ถ้ามี | UX-001, UI-002; B-01/B-08 ยืนยันได้ในเดโม |
| E-02 เลือกวันเข้าแต่ไม่มีวันออก | เตือนให้เลือกวันออกหรือล้างวันที่ ไม่ส่งช่วงวันที่ครึ่งเดียวไปใช้เป็นรายการจอง | สถานที่ วันเข้า และผู้เข้าพัก | B-07 พบ alert ใน Mobile; เป้าหมายต้องสื่อสารเทียบเท่ากันทั้ง Desktop/Mobile |
| E-03 ช่วงวันที่ผิดรูปแบบ/ย้อนหลัง | ให้แก้ช่วงวันที่และอธิบายจุดผิด ห้ามแสดงวันว่างหรือราคาจองยืนยันจากข้อมูลไม่ถูกต้อง | ข้อมูลอื่นที่ยังใช้ได้ | Source ปิดวันก่อนวันนี้ใน picker; ไม่ได้ทดสอบการส่งข้อมูลผิดผ่านระบบจริง |
| E-04 จำนวนคนไม่ครบ/ไม่เหมาะกับที่พัก | การ browse ไม่บังคับจำนวนคน; ใช้จำนวนผู้เข้าพักรวมไม่แยกผู้ใหญ่/เด็ก พร้อมสัตว์เลี้ยงแยกตาม Q-05; ก่อนจองต้องแจ้งข้อมูลที่ต้องแก้และตรวจความจุ/นโยบายสัตว์เลี้ยงจริง | จำนวนผู้เข้าพักรวม สัตว์เลี้ยง และที่พัก | เดโมยังแยกผู้ใหญ่/เด็ก/สัตว์เลี้ยงและจำกัดแต่ละตัวนับ 0–50 ซึ่งไม่ใช่รูปแบบหรือกฎธุรกิจเป้าหมาย |
| E-05 ไม่มีผลค้นหา | แสดง no-results พร้อมแก้หรือล้างเงื่อนไข อย่าแสดงเป็นระบบล่ม และอย่าล้างทุกช่องโดยไม่บอก | เงื่อนไขล่าสุด | B-09 พบ 0 หลังและคำแนะนำ; PAGE-010 กำหนดสถานะตามบริบท |
| E-06 Guest เริ่มจอง | รักษาที่พัก วันที่ ผู้เข้าพัก และปลายทางเดิมเฉพาะ flow ต่อเนื่อง → Auth → คืนบริบท → ตรวจราคา/วันว่างใหม่; ไม่กู้เมื่อเกิดเหตุใน Q-03 | Booking Intent ที่ยังใช้ได้ตาม journey-map | UX-004, UXF-004, PAGE-005, EXEC-007 และ Q-03; เป้าหมาย ยังไม่มีระบบให้ทดสอบ |
| E-07 ยกเลิก Auth | กลับ Detail ที่เริ่มจองพร้อมค่าที่เลือก; Auth ที่เปิดจาก Header ให้กลับหน้าที่เปิดมา โดยไม่สร้างรายการจองหรือข้อความสำเร็จ ถ้าเกิดเหตุ Q-03 แล้วให้เริ่มข้อมูลจองใหม่ | Intent ที่ยังใช้ได้และต้นทาง ไม่กู้ draft ที่ล้างแล้ว | Q-02 อนุมัติแล้ว; ปัจจุบัน Auth เดโมปิดหน้าต่างได้ แต่ไม่มี booking intent ให้คืน |
| E-08 Login/register ไม่สำเร็จ | ให้แก้ฟอร์มหรือลองใหม่โดยไม่เสียบริบทการจอง ไม่แสดงรายละเอียดระบบภายในหรือข้อมูลบัญชีอื่น | บริบทจองและข้อมูลฟอร์มที่เหมาะสม ไม่เก็บรหัสผ่านเป็น intent | เป้าหมาย; source เดโมตรวจ required/รูปแบบและยืนยันรหัสผ่าน ไม่พิสูจน์ Auth จริง |
| E-09 Intent หรือ session หมดอายุระหว่างทาง | หยุดขั้นตอนที่ต้องใช้สมาชิก ไม่กู้ Booking Intent เดิม แจ้งให้เริ่มเลือกข้อมูลจองใหม่และ login เมื่อจำเป็น; ไม่ส่งคำขอชำระเงินซ้ำอัตโนมัติ | ไม่รักษา draft intent; รายการจองจริงยังดูได้หลังตรวจสิทธิ์ | Q-03 ยืนยันแล้ว; การล้าง intent ไม่ลบรายการจองหรือสถานะชำระเงินที่สร้างจริง ไม่มี session จริงในเดโม |
| E-10 ราคาเปลี่ยนหลัง login หรือแก้ข้อมูล | แสดงว่าราคาเปลี่ยน ให้ตรวจรายการล่าสุดก่อนเดินต่อ ไม่ยืนยันยอดเดิมหรือคิดเงินทันที | ที่พัก/วันที่/ผู้เข้าพัก และบริบทว่าราคาเดิมเปลี่ยน | PRIN-007, UXF-004; เป้าหมาย แหล่งราคาอ้าง OPEN-007 |
| E-11 ที่พักไม่ว่างหรือยังตรวจสอบไม่ได้ | แยก “ไม่ว่าง” จาก “ยังตรวจสอบไม่ได้”; ให้แก้วัน เลือกอื่น หรือ retry ตามเหตุ ไม่แสดงพร้อมจองจากราคาเริ่มต้น | ค่าที่เลือกเพื่อแก้ต่อ | PRIN-007; OPEN-006/OPEN-007 ยังเปิด ไม่กำหนด hold/locking ในงานนี้ |
| E-12 ที่พัก/รายการจากลิงก์ตรงหาไม่พบ | อธิบายว่าหารายการไม่พบหรือเปิดไม่ได้ มีทางกลับค้นหา; ถ้าต้อง login ให้คืนปลายทางหลังยืนยันตัวตนก่อนตรวจใหม่ | บริบทค้นหา/รหัสอ้างอิงที่เหมาะสม | ข้อเสนอระดับ UX; ไม่มี route รายละเอียดหรือ booking จริงให้ทดสอบ |
| E-13 ชำระเงินยกเลิก/ไม่สำเร็จ/ยังรอผล | แยกแต่ละกรณีตามผลที่ตรวจสอบได้ แสดงสถานะจองและชำระเงินแยกกัน; ปุ่ม retry ต้องไม่สร้างการเรียกเก็บซ้ำโดยไม่ตรวจสถานะเดิม | รหัสรายการที่ตรวจสอบได้และสถานะล่าสุด | PAGE-004/PAGE-007; OPEN-003 ยังไม่ยืนยันสัญญาผู้ให้บริการ ไม่กำหนดชื่อ status/API |
| E-14 ดูเหมือนชำระเงินสำเร็จแต่สถานะจองยังไม่ยืนยัน | แสดงตามข้อมูลที่ยืนยันได้ เช่น รอตรวจสอบ ห้ามใช้หน้ากลับจากผู้ให้บริการแทนหลักฐานธุรกรรม; เสนอทางดูสถานะรายการอีกครั้ง | รหัสอ้างอิงรายการ ไม่เก็บข้อมูลบัตร | PAGE-007, PRIN-007; เป้าหมาย ไม่จำลองคำยืนยันจองสำเร็จจาก URL |
| E-15 Back/reload/ปิดแท็บ/เปิดแท็บใหม่ | Results ยังอ่านเงื่อนไขค้นหาจาก URL ได้ แต่ไม่กู้ Booking Intent หลัง reload/ปิดแท็บ/หมดอายุและไม่เพิ่มการกู้ข้ามแท็บ; Back ภายใน flow ที่ยังใช้ได้คงบริบทตามปกติ | ค้นหา/filters/page ตาม URL เป็นคนละเรื่องกับ draft booking; ต้องเริ่มข้อมูลจองใหม่หลังเหตุ Q-03 | Q-03 ยืนยันแล้ว; การอ่านรายการจองที่สร้างจริงไม่ใช่การกู้ intent |
| E-16 Guest กดหัวใจหรือเปิด Favorites | ต้อง login ก่อนดูหรือจัดการ Favorites ไม่บันทึกรายการ Guest ชั่วคราว; ถ้ายกเลิก Auth กลับหน้าต้นทางโดยไม่เปลี่ยนรายการโปรด การ browse ที่พักยังไม่ต้อง login | ต้นทาง/ที่พักที่ต้องการใช้ใน flow Auth ต่อเนื่อง ไม่มี Guest favorites ให้รวมเข้าบัญชี | Q-01 ยืนยันแล้ว; B-03 บันทึกพฤติกรรมเดโมเดิมที่ยังไม่ตรงเป้าหมาย |
| E-17 เข้าหน้าบัญชี/รายการของผู้อื่น | ต้องไม่แสดงข้อมูลส่วนตัวหรือรายการที่ไม่มีสิทธิ์; แสดงทางไป login หรือรายการของตนตามบริบทที่ปลอดภัย | ปลายทางภายในที่ตรวจสอบได้ | เป้าหมายระดับ UX ไม่ใช่ผลตรวจ authorization/RLS; การแยกข้อความและกลไกเป็นงานระบบภายหลัง |
| E-18 Offline/โหลดข้อมูลผิดพลาด | แยกจากรายการว่าง แจ้งว่าข้อมูลยังตรวจไม่ได้ ให้ retry โดยคงค่าที่เลือก ไม่แสดงผลสำเร็จจากข้อมูลเก่า | เงื่อนไขค้นหาและบริบทที่ไม่อ่อนไหว | PAGE-010; ไม่ได้ทดสอบ offline/API error เพราะเดโมใช้ fixtures |
| E-19 ลืมรหัสผ่าน | เดโมต้องบอกตามจริงว่ายังไม่ส่งอีเมล; ระบบเป้าหมายต้องกลับมาทำเส้นทางเดิมได้ตามนโยบายที่ออกแบบใน Auth task | บริบทนำทางที่เหมาะสม ไม่เก็บข้อมูลลับใน intent | B-04 พบข้อความเดโม; ไม่อนุญาตสร้างระบบ reset password ใน UXD-001 |

## 2. ลำดับคืนบริบทหลัง Auth

```mermaid
flowchart TD
  START["กำลังเข้าหน้าหรือทำรายการที่ต้องเป็นสมาชิก"] --> KEEP["รักษาบริบทที่จำเป็น"]
  KEEP --> AUTH["Auth"]
  AUTH --> OUTCOME{"ผลการเข้าสู่ระบบ"}
  OUTCOME -->|ยกเลิก โดยบริบทยังใช้ได้| CANCEL["กลับต้นทางเดิมตาม Q-02 ไม่ยืนยันรายการ"]
  OUTCOME -->|ไม่สำเร็จ โดยบริบทยังใช้ได้| RETRY["แสดงข้อผิดพลาดให้แก้ โดยคงบริบท"]
  RETRY --> AUTH
  AUTH -->|reload / ปิดแท็บ / intent หรือ session หมดอายุ| RESET["ไม่กู้ Booking Intent เริ่มเลือกข้อมูลจองใหม่"]
  OUTCOME -->|สำเร็จ| CONTEXT{"คืนบริบทได้และยังใช้ได้?"}
  CONTEXT -->|ไม่ได้| RECOVER["แจ้งสิ่งที่ต้องเลือกใหม่ ไม่เดาข้อมูลจอง"]
  CONTEXT -->|ได้| VERIFY["ตรวจสิทธิ์ ข้อมูลที่พัก ราคา และวันว่างตามปลายทาง"]
  VERIFY --> RESULT{"ข้อมูลล่าสุดพร้อมเดินต่อ?"}
  RESULT -->|ไม่พร้อม| CHANGE["อธิบายเหตุ ให้แก้หรือเลือกใหม่"]
  RESULT -->|พร้อม| CONTINUE["กลับขั้นตอนเดิม ไม่ถือว่าจองหรือชำระเงินเสร็จ"]
```

ทางกลับเมื่อยกเลิกยืนยันตาม Q-02 และขอบเขตการรักษา intent ยืนยันตาม Q-03 แล้ว แผนผังไม่ล็อกกลไกสถานะชั่วคราว ระยะเวลา session หรือการสร้าง reservation จริง การคืนบริบทต้องไม่กลายเป็นการ redirect ไปปลายทางภายนอกตามข้อมูลที่ผู้ใช้ป้อนโดยไม่ตรวจสอบ

หาก flow Auth ในอนาคตจำเป็นต้อง reload หน้า ต้องเคารพ Q-03 และไม่แอบกู้ intent จาก storage; ต้องออกแบบให้ผู้ใช้รู้ว่าต้องเลือกข้อมูลจองใหม่ การล้าง draft intent ไม่กระทบรายการจองจริง ข้อมูลบัญชี หรือรายการโปรดของสมาชิก

## 3. ข้อสรุปเฉพาะงานที่ภูยืนยัน

| รหัส | เรื่อง | ข้อสรุปจากภูเมื่อ 2 พฤศจิกายน 2026 | ผลต่อเส้นทาง |
|---|---|---|---|
| Q-01 | การใช้ Favorites | ต้อง login เท่านั้น ไม่อนุญาต Guest favorites ชั่วคราว | Guest ผ่าน Auth ก่อนดูหรือจัดการ Favorites; ไม่มีรายการ Guest ให้รวมกับบัญชี การ browse ยังเปิดสาธารณะ |
| Q-02 | ปลายทางเมื่อยกเลิก Auth | อนุมัติข้อเสนอ: กลับ Detail ที่เริ่มจองพร้อมค่าที่เลือก; ถ้าเปิด Auth จาก Header กลับหน้าที่เปิดมา | ใช้ค่าที่เลือกได้เฉพาะเมื่อยังอยู่ใน flow ที่ไม่ถูกล้างตาม Q-03 |
| Q-03 | Intent หลัง reload/ปิดแท็บ/หมดอายุ | ไม่ต้องรักษาหรือกู้ intent หลังเหตุเหล่านี้ | รักษาเฉพาะ flow การนำทาง/Auth ที่ต่อเนื่องและยังใช้ได้; ไม่เพิ่มการกู้ข้ามแท็บ; แยก draft intent จาก Results URL และรายการจองจริง |
| Q-04 | เมนูเนื้อหาและ “ลงประกาศวิลล่า” ใน Footer เดิม | อนุมัติการเก็บเป็น supporting inventory และพิจารณาขอบเขตเนื้อหาแยก ไม่เพิ่ม owner portal ใน 10 templates นี้ | ไม่สร้างหน้าหรือ flow ผู้ลงประกาศใน UXD-001 |
| Q-05 | รูปแบบผู้เข้าพักและสัตว์เลี้ยง | ใช้จำนวนผู้เข้าพักรวม ไม่แยกผู้ใหญ่/เด็ก และมีสัตว์เลี้ยงแยกจากจำนวนคน | ใช้รูปแบบเดียวกันในค้นหา/Detail/Checkout และ intent ที่ยังใช้ได้; ไม่ใช้รูปแบบผู้ใหญ่/เด็กเดิมของเดโมเป็นเป้าหมาย |

Q-01 ถึง Q-05 ได้ข้อสรุปเฉพาะงานแล้วใน review-2 โดยไม่เปลี่ยนแบรนด์หรือ page templates ต่อมาภูอนุมัติเอกสารทั้งชุดตามบันทึกตรวจรับข้างต้น การอนุมัตินี้ไม่เริ่ม task ถัดไป

Q-05 ยืนยันรูปแบบจำนวนผู้เข้าพัก ส่วนกฎความจุ/สัตว์เลี้ยงและฟิลด์ข้อมูลติดต่อสมาชิกที่ขาดยังเป็นรายละเอียดงานโดเมน/สมาชิกภายหลัง ไม่ใช้ขอบเขตผู้ใหญ่/เด็กหรือค่า 0–50 จากเดโมเป็นกฎจริง และไม่บังคับกรอกข้อมูลติดต่อเดิมซ้ำโดยไม่จำเป็นตาม PAGE-004

## 4. ความสัมพันธ์กับรายการ OPEN เดิม

อ้างอิง [open-decisions.yaml](../../decisions/open-decisions.yaml) โดยไม่เปลี่ยนสถานะรายการเหล่านั้น:

| รายการ | วิธีจัดการใน UXD-001 |
|---|---|
| OPEN-001 contrast ชมพู/ขาว | บันทึกข้อจำกัด ไม่เลือกสี CTA ใหม่หรือรับรอง accessibility จาก journey map |
| OPEN-002 / OPEN-005 ภาพอ้างอิงและต้นทาง | ใช้โค้ด/local demo เป็นหลักฐานสภาพปัจจุบัน ไม่ใช่ approved visual baseline; การสำรวจ IA ไม่ต้องรอภาพครบ |
| OPEN-003 BeamCheckout | อธิบายผลสำเร็จ/ล้มเหลว/รอยืนยันในระดับ UX ไม่เดา API, webhook หรือความสามารถทดสอบ |
| OPEN-004 Workers runtime | รอบนี้ตรวจ Next.js dev เท่านั้น ไม่ยืนยันว่า Auth/Checkout/ภาพ/ธุรกรรมทำงานบน Workers |
| OPEN-006 hold/concurrency | ระบุทางกลับเมื่อราคา/วันว่างเปลี่ยน ไม่กำหนด TTL หรือวิธีล็อกข้อมูล |
| OPEN-007 catalog/price/availability authority | ใช้สถานะ “ยังตรวจสอบไม่ได้” เมื่อไม่มีข้อมูลยืนยัน ไม่แสดง instant booking จาก fixtures |

ความไม่ตรงกันของ dependency การอนุมัติรายหน้ากับ UID-009 ที่พบก่อนหน้าไม่ได้แก้ใน UXD-001 และไม่ขวางการจัดทำเอกสาร task นี้ ต้องทบทวนก่อนใช้ gates เริ่ม frontend ที่เกี่ยวข้อง

## 5. รายการตรวจสำหรับการส่งมอบ

- [x] เส้นทาง Guest และ Member ครอบคลุม browsing/search/detail/auth/checkout/confirmation และหน้าบัญชีตามขอบเขต
- [x] แยกการ browse โดยไม่มีวันออกจากการตรวจข้อมูลก่อน booking
- [x] ระบุ Property ID/วันที่/ผู้เข้าพักที่รักษาข้าม Auth เฉพาะ flow ต่อเนื่อง พร้อมข้อยกเว้น Q-03 และการตรวจราคา/วันว่างใหม่
- [x] สะท้อน route, หน้าต่างเดโม, Header/Footer และข้อจำกัดจากโปรเจกต์ปัจจุบัน
- [x] บันทึกการสำรวจ Desktop/Mobile และการทบทวน accessibility ที่ทำจริง พร้อมส่วนที่ไม่ได้ทดสอบ
- [x] แยก booking/payment status และไม่เดารายละเอียด provider, hold หรือ catalog
- [x] ภูให้ข้อสรุป Q-01 ถึง Q-05 และอัปเดตเส้นทาง/ข้อมูลให้สอดคล้องกันใน review-2
- [x] ภูอนุมัติเอกสาร UXD-001 รุ่น review-2 เมื่อ 2 พฤศจิกายน 2026

รายการที่ติ๊กแล้วหมายถึงมีเนื้อหาและการตรวจรับชุดเอกสาร ไม่ใช่ระบบที่ implement หรือผ่าน E2E แล้ว การอนุมัติแผนเริ่มทำงานครั้งก่อนแยกจากการตรวจรับผลงาน review-2 ครั้งนี้ และยังไม่เริ่ม UXD-002, DSD-001 หรือ task อื่น
