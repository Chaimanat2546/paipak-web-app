# Home Auth Desktop · ข้อเสนอรหัสผ่านรุ่น1

> ข้อขั้นต่ำ15ตัวในเอกสารนี้ถูกแทนด้วย [เจ้าของกำหนด8ตัวสำหรับสมัคร/ตั้งใหม่](home-auth-password-minimum-decision.json) แล้ว ข้ออื่นยังเป็นข้อเสนอ ไม่ใช่การอนุมัติจากคำตอบเรื่องความยาว [ต้นฉบับ](home-auth-password-policy-r1-original.md.txt) เก็บbytesเดิม

5 พฤศจิกายน2026 · DSD-001/C2 · **PROPOSED — รอเจ้าของตัดสินใจ**

## ข้อเสนอที่ใช้ในแบบ

- สมัครด้วยอีเมลและตั้งรหัสใหม่: ขั้นต่ำ15ตัวอักษร ไม่บังคับสูตรตัวใหญ่/ตัวเล็ก/ตัวเลข/สัญลักษณ์
- รองรับรหัสผ่านยาวอย่างน้อย64ตัวอักษร ขอบเขตสูงสุดที่แน่นอนต้องสอดคล้องระบบAuthที่เลือกภายหลัง ไม่ตัดรหัสให้สั้นเอง
- รองรับpassword manager/autofillและการวางข้อความ มีแสดง/ซ่อนตามขอบเขตG0 และconfirmationบังคับตามคำตอบที่รับแล้ว
- ออกแบบผลไม่ยอมรับรหัสผ่านที่พบบ่อย/รั่วไหลเป็นcontractสำหรับงานAuthภายหลัง ไม่สร้างblocklist/APIหรืออ้างว่าตรวจได้จริงในPencil
- Loginตรวจว่ากรอกข้อมูลแล้ว ไม่ใช้กฎตั้งรหัสใหม่ไปตัดสินข้อมูลบัญชีเดิมเอง

## หลักฐานและเหตุผล

อ่านแนวทางทางการ [NIST SP 800-63B-4, Password Verifiers §3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) ผ่านFirecrawlวันที่5พฤศจิกายน2026 เอกสารกำหนดขั้นต่ำ15เมื่อรหัสผ่านเป็นปัจจัยเดียว แนะนำรองรับอย่างน้อย64 ไม่ใช้composition rules และให้ใช้password managers/autofillได้ โดยแนะนำให้pasteได้ นอกจากนี้กำหนดตรวจรหัสที่กำลังตั้งกับblocklistของค่าพบบ่อย/คาดเดาง่าย/รั่วไหล

ในขอบเขตที่เลือกยังไม่มีMFAสำหรับemail/password จึงเสนอ15เป็นฐานในการออกแบบ ไม่ยก8จากโค้ดเดโม ข้อนี้เป็นข้อเสนอของเอเจนต์อิงแนวทาง ไม่ใช่ข้อกฎหมายที่ระบุว่าบังคับเว็บนี้ และไม่รับรองNIST complianceจากการเลือกกฎบางส่วน

Googleมีข้อกำหนดรหัสผ่านของผู้ให้บริการเอง ไม่เพิ่มช่องตั้งรหัสผ่านเว็บในflow Googleจากข้อนี้ รายละเอียดprovider/Unicode counting/validation/credential lifecycleและbackendยังอยู่ในงานระบบภายหลัง

## จุดตัดสินใจ

1. ใช้ข้อเสนอรุ่น1เป็นข้อกำหนดRegister/Resetในแบบ
2. ขอปรับข้อเสนอ โดยระบุส่วนที่ต้องการเปลี่ยน
3. ดูตัวอย่างข้อความและกรณีผิดเงื่อนไขก่อนตัดสินใจ

ไม่ออกแบบUIใหม่หรือแก้code/backendจากเอกสารข้อเสนอนี้
